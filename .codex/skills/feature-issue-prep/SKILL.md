# 機能イシューの仕様整理

ユーザーの要件と現在のリポジトリの状態をもとに、確認しやすい機能仕様を作成します。

## 手順

1. 編集前にリポジトリの `AGENTS.md` と関連するローカル指示を読みます。渡された要望をもとに、現在のコード（`routes/`・`app/`）と`docs/design/`の設計書一式を確認し、決める必要のある事項が残っていないか確かめます。ユーザーが指定した範囲と既存のプロジェクト規約を守ります。
   - 対象機能の受け入れ条件が`docs/design/acceptance.md`にある場合は、文言を言い換えず、そのままイシューに記載します。設計書とイシューの表現を揃えてください。
2. まず`docs/design/`から関連する設計書を探し、必要に応じて`docs/spec.md`と`mockup/`も確認します。そのうえで、関係するスキーマ、モデル、シーダー、ルート、コントローラー、ビューを調べます。名前や動作はソースで確かめ、指定されたシーダー・テーブル・クラスが存在すると決めつけません。
3. ユーザーが指定したパスにMarkdownファイルを作ります。パスの指定がなければ、プロジェクトで使われている仕様書の保存先を選びます。複数の候補で結果が大きく変わる場合に限り確認します。
4. 文書では、次の項目を読み分けられるように整理します。
   - 確定した要件と受け入れ条件
   - 会話ですでに合意した決定事項
   - 提案であることを明記した初期案
   - 実装に影響する未決事項
5. ER図はユーザーが指定したエンティティだけを含めます。既存テーブルは明示的に求められた場合に限り図に含め、外部キーで関連していても指定外のテーブルは省きます。必要であれば、図の対象を限定した理由を図の外に記します。既存テーブルか追加テーブルかを明示し、追加数を正確に記載します。
6. シードデータが関係する場合は、指定されたシーダーと、実際に登録しているモデル・テーブルを確認します。名前や現在の動作が用途と食い違う場合は、現状と最小限の安全な対応案を説明します。仕様整理の段階で、アプリケーションコードを黙って改名・転用・編集しません。
7. 頼まれていない実装には踏み込みません。イシュー準備の一環として、マイグレーション、モデル、ルート、テストを作成しません。
8. 最後に差分を確認し、空白エラーがないか `git diff --check` を実行します。文書だけの作業では、ユーザーから頼まれない限りテストを実行しません。

## 決定事項と未決事項の書き方

- 受け入れ条件の意味を弱めず、それぞれ検証できる表現にします。
- 明示された対象外の事項や維持する既存動作は、独立した項目に記載します。
- 「名前は任せる」などユーザーが判断を委ねた場合だけ、定型的な選択を確定します。それ以外は、妥当な初期案を提案として明記します。
- 実装や受け入れ判定に影響する未回答の選択肢だけを挙げます。会話ですでに回答されたことは再質問しません。
- リポジトリの実態と要望に食い違いがある場合は、現在のコードの動作と必要な変更を説明します。提案を実装済みとして書きません。

## データ設計

チャンネル、メンバー、メッセージ、返信などのテーブルや関連を提案する場合は、まず `docs/design/data.md` と既存スキーマを確認します。既存の設計・スキーマを保ち、依頼と受け入れ条件が必要とする変更だけを提案します。指定されていないエンティティや関連を推測で足さず、未決事項として示します。
