# Issueの実装準備

最初にmainを最新化して対象Issueの作業ブランチを準備する。その後、既存Issueの資料と現状を読み、作業規模に応じてPlanモードで計画を立てるか、変更概要だけを伝えるかを分ける。どちらも提示した内容への承認を得てから着手する。計画だけの依頼では実装しない。

## 0. mainを最新化し、作業ブランチを準備する

- AGENTS.mdと関連するローカル指示を読み、対象Issueを特定する。ブランチ名はAGENTS.md「ブランチとプルリクエストの方針」に従う。Issueが不明なら番号やURLを質問し、無関係なブランチを作らない。
- 現在のブランチ、ステージ済み・未ステージ・未追跡の変更、進行中のマージやリベースを確認する。既存の変更を自動でコミット・stash・破棄せず、既存ブランチも改名・上書きしない。変更を今回のブランチへ持ち込むか判断できない場合や、進行中のGit操作がある場合は、その状況と必要な判断を伝える。
- 新規着手では、`git fetch origin`でリモートの状態を取得し、安全に切り替えられることを確認して`git switch main`、`git merge --ff-only origin/main`を行う。mainとorigin/mainが同じコミットであることを確認してから、規約に沿った名前で`git switch -c <ブランチ名>`を行う。mainに独自コミットがある・履歴が分岐している場合は、自動でreset・rebase・マージコミットを作らず、差分を示して扱いを確認する。
- 対象Issueの作業ブランチが既にある場合は、変更・履歴・既存PRを確認して再開できるか判断する。新規作成の手順を繰り返さず、mainの取り込みや履歴の書き換えも自動で行わない。対象ブランチを特定できなければ質問する。
- このブランチ準備はスキル呼び出しに含まれ、実装計画への承認前に行う。環境の実行承認は守り、Gitの接続・権限エラーを設定変更やforce操作で回避しない。失敗した場合は原因と完了した範囲を伝え、ブランチ準備に依存しない読み取り調査だけを進める。
- 準備後は現在のブランチ名と、最新化の結果または既存ブランチを再利用した旨を短く共有し、Issue・設計・現状の照合へ進む。

## 1. Issue・設計・現状を照合する

- AGENTS.mdと関連するローカル指示を読み、対象Issueの本文・受け入れ条件・現在の会話での決定を確認する。Issueが特定できなければ番号やURLを質問する。
- AGENTS.mdの資料案内を使い、関連する設計書と画面見本を確認する。要件と対象範囲、画面、データ、権限・ルート、入力、例外、受け入れ条件の対応を追う。
- 現在のルート、モデル、スキーマ、コントローラー、ビュー、Seeder、テスト、依存パッケージを調べる。ファイルや機能が存在すると決めつけず、既存実装と追加が必要な部分を区別する。
- Issueの古い記述と会話の追加決定が違う場合は、その差を明示する。確定済みの設計やユーザーの判断を、未決事項に戻さない。

## 2. 読み終えたら進め方を分ける

Issue・設計・現状の確認が終わったら、影響範囲と判断の必要性で次のように分ける。行数やファイル数だけで小さい件と判定しない。

| 作業 | 進め方 |
| --- | --- |
| 計画が必要な件：複数の処理の連携、技術選定、保存・権限・入力仕様などの設計判断が必要 | Planモードに入り、未決事項を解消して計画を提示する。ユーザーの承認を得てから実装へ移る。 |
| 計画を出すほどではない小さい件：仕様や責務を変えない局所的な誤字・説明・コメントの修正など | Planモードには入らず、何をどこへ変更し、どう確認するかを短く伝える。ユーザーの承認を得てから着手する。 |

- ユーザーがPlanモードや計画の提示を指定した場合は、その指定を優先する。
- 小さい件では、以降の範囲・技術・設計の確認を必要な部分に絞り、詳細な計画書や技術選定表は作らない。調査で設計判断や広い影響が見つかったら、計画が必要な件として扱い直す。
- 上記のブランチ準備を除き、承認前は読み取り調査と会話での提案にとどめる。設計書の編集、パッケージ追加、アプリの変更には着手しない。
- Planモードへ切り替える手段がない環境では、その制約を伝えて会話上で計画を提示し、承認を待つ。実際に切り替えていないのにPlanモードに入ったと説明しない。

## 3. 今回の範囲と未決事項を整理する

- 「今回作る」「後続Issueへ回す」「今回の対象外」を分ける。遷移先や共通レイアウトが必要でも、後続機能まで完成させる前提にしない。認証確認用の見出しなど、受け入れ確認に必要な最小範囲を提案する。
- 設計や既存の回答で決まっていない、動作・保存・権限・検証・技術選定に影響する事項を実装前に質問する。推奨案とその理由、別案との違いを短く添える。
- 質問は関連するものをまとめ、判断しやすい選択肢にする。回答を待つ間は依存しない調査を進め、未回答の事項に依存する設計や実装は確定しない。
- 単なる作業手順の選択と、ユーザーが決める仕様を区別する。既に承認された事項を聞き直さず、任された定型的な選択は理由を添えて進める。

## 4. 何を使うか、材料と結論を示す

- Laravel標準機能、追加パッケージ、自作する部分を区別し、それぞれの担当処理と選ぶ理由を示す。必要に応じて、コントローラー、FormRequest、ミドルウェア、モデル、Blade、Seederなどへの責務の配置を説明する。
- 判断材料は、ユーザー指定、関連設計、既存コード、composer.json・composer.lock、導入済みソース、必要に応じた公式ドキュメントとする。プロジェクトのLaravel・PHPとの互換性を確認し、最新版という理由だけで選ばない。
- 標準機能や既存パッケージを拡張する場合は、どの処理を標準に任せ、どこだけ独自対応するかを示す。初期設定や自動登録ルートも確認し、不要な機能が公開されないよう、有効にする機能を絞る。
- 選定結果には根拠の参照先を付ける。このセッションや別機能で選ばれたライブラリ・上限値・試行制限を、他のIssueの既定値にしない。

## 5. 設計の更新内容と計画の持ち方を決める

- 新たに決まった動作や物理設計は、対応するdocs/design/の更新案として整理する。変更する箇所と理由、入力条件・画面の案内・受け入れ観点などの影響先を示す。承認後は、実装より先に設計書へ反映する。
- 設計書にある要件を計画書へ写さず、ファイル・見出し・F／SC／Q／AC／TPなどのIDで参照する。計画には差分、作業順、判断理由、未決事項、検証方法を残す。
- 計画の保存先は、ユーザー指定やリポジトリの既存方式に従う。指定がなければ会話中の計画を使い、永続的な計画書を自動で増やさない。設計上の決定は、承認後に設計書へ記録する。
- 選んだ計画の持ち方と理由を説明する。仕様の正本、判断の記録、作業の順序、確認結果の置き場を読み分けられるようにする。
- 資料にないことを既存要件として書かない。新しい決定と提案を区別し、判断基準が足りない場合は必要な材料を明示する。

## 6. 計画または変更概要を提示し、承認を待つ

計画では次の内容を、対象Issueの大きさに応じて短く示す。

- 対象Issue・設計の参照先と、今回作る範囲・作らないもの
- 計画の置き場と、その方式を選んだ理由
- 使用する技術・Laravelの機能、それを決めた材料と結論
- 設計書の更新箇所と理由
- 実装する単位と依存関係に沿った順序
- 受け入れ条件ごとの確認方法、入力エラー・権限不足・例外などの関連する検証観点
- 残る未決事項、必要な回答、現時点では確認できないこと

検証コマンドやデータの扱いはAGENTS.mdとテスト設定を参照し、計画した確認と実行済みの確認を区別する。実行していないテストや画面操作を確認済みと書かない。

小さい件では、上記の一覧を展開せず、変更箇所・変更内容・確認方法を短く伝えて承認を求める。

必要な回答が未解決なら、影響する実装には進まない。未決事項への回答と、提示した計画・変更概要への着手承認を区別する。実装まで依頼されていても、計画または変更概要への承認が得られるまでは着手しない。無回答や時間の経過を承認と扱わない。

承認を得たら、計画が必要な件はPlanモードを終了して実装へ移り、小さい件は提示した変更に着手する。どちらも必要な設計更新を実装より先に行う。承認済みの範囲を再度確認せずに進め、範囲や仕様を変える必要が出た場合は変更案を示して改めて承認を得る。準備のための依存調査を、パッケージ追加やアプリの変更にすり替えない。

このSkillは実装着手までを扱う。mainの最新化と作業ブランチの準備を含む。環境構築、Docker・Gitの設定や接続トラブル対応、PR作成・マージは含めない。
