# Playwright MCP による画面 UAT

ユーザーが指定した画面・アカウント・受け入れ条件を Playwright MCP で確認し、結果を証拠付きで返す。ユーザーがコード変更を禁止した場合は、アプリのコードや設定を変更しない。

## 受け入れ条件と確認用アカウント

受け入れ条件は `docs/design/acceptance.md` にあります。イシュー番号や機能名（認証・チャンネル・メンバー管理・メッセージ・スレッド・検索・公開API）だけを指定された場合は、このファイルから該当機能の条件を読み取って対象にします。確認を始める前に、同じファイルの「確認の前提」も読んでください。

初期データを使う場合のアカウントは次のとおりです。

- `sato@example.com` / `password`：佐藤 太郎。「開発」と「採用プロジェクト」の作成者。
- `suzuki@example.com` / `password`：鈴木 花子。「採用プロジェクト」のメンバー。
- `takahashi@example.com` / `password`：高橋 健。「採用プロジェクト」の未参加者。

他人の操作制限や、他人に見えてはいけない情報を確認するときは、該当するアカウントに切り替えて比較します。プライベートチャンネルの非開示確認には高橋を使います。

## 実施

1. Playwright MCP で指定 URL を開き、ページのスナップショットを読んで現在のログイン状態と画面を確認する。操作は表示された要素を使い、必要に応じてスナップショットを取り直す。
2. 受け入れ条件をユーザーが指定した順で確認する。アカウント別の認可を調べる場合は、指定された各アカウントにログインし、同じ対象データで表示と操作可否を比較する。
3. 状態を変える操作は、確認に必要な最小限にする。作成したテストデータは、同じテストアカウントで削除するなど、既存データに触れずに後片付けする。既存データの削除や、認可を迂回するリクエスト送信はしない。後片付けできない場合は、作成物と状態を報告する。
4. 各条件の確認直後にスクリーンショットを保存する。ユーザーの指定がなければ作業フォルダー内の `uat-shots/` に保存し、必要ならフォルダーを作成する。名前は `01_短い条件名.png` のように連番と条件が分かるものにする。全ページが必要な証拠では full-page を使う。
5. 画面表示、操作後の状態、件数の変化などを組み合わせて判断する。空入力の検証では、エラー表示だけでなく、項目の `required`、`checkValidity()`、`validationMessage` と、送信前後の件数も確認できる。ブラウザー標準の検証メッセージはアクセシビリティスナップショットや画像に写らない場合があるため、その場合は取得できたメッセージを報告に書く。
6. 削除などの権限確認では、他人のデータに操作ボタンがないことは画面上の証拠として扱う。認可拒否のサーバー側動作まで確認するには、安全に実行可能で、データを壊さない方法が必要。拒否を確認するためだけに削除リクエストを直接送ってはならず、サーバー認可まで未確認ならその範囲を明記する。

## 接続エラー

Playwright MCP がブラウザー使用中などで操作できない場合、タブ操作やスナップショットを一度試して状況を確かめる。解消しないなら別の操作手段に切り替えず、未実施条件とエラーを報告する。確認していない項目を推測で合格にしない。

## 報告

受け入れ条件を一行ずつ、**判定**（満たす／満たさない／未確認）、画面で観測した根拠、対応するスクリーンショットへのリンクとともに報告する。サーバー側挙動など未確認範囲があれば同じ行に明記する。最後に、後片付けの結果とコードを変更したかを簡潔に記す。
