# PRレビュー

指定されたPRを読み、仕様外の追加、既存機能への影響、実装上の問題を報告する。レビューの依頼だけでは、コードの修正、コミット、push、GitHubへのコメント投稿は行わない。

## 対象を確認する

- PR番号が指定されていれば、そのPRを使う。マージ済みPRから選ぶ依頼なら `gh pr list --state merged` で一覧を確認する。
- `gh pr view <番号> --json title,body,baseRefOid,headRefOid,files,url` で対象と変更ファイルを確認し、`gh pr diff <番号>` で差分を取得する。
- 長い差分が省略された場合は、一時ファイルへの保存やファイル単位の取得で未読部分を確認する。
- ユーザーが説明した機能とPRの内容が異なる場合は、その食い違いを先に伝える。別のPRに勝手に切り替えず、確認できる範囲と不足している情報を報告する。
- 周辺コードはPRのheadコミット、削除前のコードはPR差分の比較元を使う。ローカルにコミットがあれば `git show <SHA>:<パス>` で読み、現在の作業ツリーと混同しない。
- 過去のPRと現在の作業ルールを比較する場合は、当時の問題と現在の方針との差を区別する。

## 1. 設計書と突き合わせる

- `AGENTS.md`と`docs/design/`の設計書一式を確認する。受け入れ条件は`acceptance.md`、画面は`screens.md`、テーブルは`data.md`、権限とAPIは`permissions-api.md`にある。`features.md`で対象範囲、`questions.md`で確定事項と未決事項、`behavior.md`で状態・例外・同時操作を確認する。設計書が無い機能は、そのIssueの受け入れ条件を照合先にし、設計不足も報告する。
- 画面、ルート、保存データ、認証・認可、入力条件、受け入れ条件を差分と照合する。
- 設計書に書かれていない機能や設定が増えていないか確認する。特に`composer.json`の依存・スクリプト・設定と`composer.lock`の変更を読む。
- 設計書にない実装や不一致を見つけたら、`AGENTS.md`の「コードではなく設計書を先に直す」方針に従い、設計上の決定・更新が必要な場所として報告する。レビュー中に設計やコードを書き換えず、未決事項を独自に確定しない。
- 参照先が見つからない場合は、照合できない理由と必要な資料を報告する。関係が不明な教材、生成物、その他のファイルも目的の確認が必要な箇所として挙げる。

## 2. 触っていないはずの場所を、消えた行から見る

次の5つは、変更対象でない場合も差分を確認する。

1. `routes/web.php`
2. `routes/api.php`
3. `app/Policies/`
4. `database/migrations/`
5. `config/`

- まず削除行を読み、認証、認可、入力条件、データ取得、設定、既存操作が失われないか確認する。その後、追加行による置き換えを追う。
- 認証グループからのルート移動、Policy呼び出しや関連データの事前取得の削除、実行済みマイグレーションの変更、既存設定の消失を確認する。
- 制限の追加で従来のデータを編集できなくなるなど、既存利用者への影響も見る。
- 差分がなければその事実を報告する。判断に必要な周辺コードも確認する。

## 3. 実装の中身を読む

次の順で確認する。

- **N+1**：一覧のループが参照する関連データを追い、`with()` などで事前取得されているか確認する。
- **認可の置き場所**：チャンネルやメッセージの編集・削除、プライベートチャンネルの閲覧がサーバー側で認可されるか確認する。ボタンの非表示だけで済ませていないかを見る。
- **マスアサインメント**：保存に渡す値とモデルの許可属性を確認する。作成者ID、メンバーID、投稿者IDなどを入力値で自由に指定できないか、認証済み利用者や認可済み操作から決定しているかを追う。
- **XSS**：本文、利用者名、入力の再表示を確認する。Bladeの未加工出力やJavaScript・HTMLへの文字列挿入は、出力先に適したエスケープまで追う。
- **CSRF**：更新系フォームの `@csrf`、webミドルウェア、CSRF除外設定を確認する。
- **入力チェック**：サーバー側の必須条件、型、上限、関連データの存在確認、日本語エラーを確認する。作成と編集で条件が揃うか、不正な値が保存されないかを見る。

## 受け取ってよいかを決める観点

3段目で中身を読むときは、次の4つも見る。問題は直さず、直したほうがよい場所として、該当行・根拠・具体的な影響を報告する。

- **名前**：Laravelの慣例（モデルは `Channel`、テーブルは `channels`、中間テーブルは `channel_user`、コントローラは `ChannelController`、ポリシーは `ChannelPolicy`）に沿うか。変数やメソッドの名前から役割が分かり、中身と一致するか。
- **重複**：同じ判断や問い合わせが複数箇所に写り、変更漏れを招く構造になっていないか。権限判定はPolicy、共通の見た目はBladeの共通部品などにまとめられるか。逆に、似ているだけで変更理由の違うものを無理にまとめていないか。
- **読みやすさ**：深いネストや長いメソッドで処理の意図が追いにくくないか。早期returnやコレクションのメソッドで明確にできるか。行数やループの有無だけで指摘せず、読む負担や変更時の間違いやすさを根拠にする。
- **設計書の言葉**：画面・テーブル・エンドポイントの呼び名が `docs/design/` と一致するか。同じものが設計書と実装で別の名前になり、対応を追いにくくなっていないか。

対象Issueの範囲と影響先に適用し、後続Issueの未実装や好みだけの書き換えを指摘しない。整形の揺れとテストの合否はフックに任せ、観点にも報告にも含めない。静的レビューをテストや画面確認を実施した扱いにせず、判断に必要な未確認事項は明示する。

## 報告形式

冒頭に対象PR、確認したコミット、静的確認か実行確認かを短く書く。対象の食い違いがあれば先に伝える。

差分全体を **受け取り可・見直しが必要・判断材料不足** で判定し、理由を短く書く。対象範囲と影響先を確認し、問題がなければ「受け取り可」、具体的な問題があれば「見直しが必要」、必要な根拠が足りなければ「判断材料不足」とする。問題と不足が併存する場合は「見直しが必要」とし、不足も添える。

上の1〜3と4観点について、確認した内容を次の列で記載する。同じ問題はまとめ、対象外の観点を網羅的に並べない。

| 観点 | 判定 | ファイル名:行番号 | 気づいたこと |
| ---- | ---- | ----------------- | ------------ |

- 判定は **要確認・OK・対象外** のいずれかにする。
- **要確認**：問題がある、または判断材料が足りない。具体的な影響や、何が不足しているかを書く。
- **OK**：実際に確認した範囲と根拠を書く。差分がないだけで機能全体の安全性を保証しない。
- **対象外**：その観点が今回の変更に適用されない理由を書く。資料不足は「要確認」にする。
- 行番号は原則として変更後を使う。削除行は「変更前」と明記する。存在しないファイルやバイナリは「—」とし、番号を作らない。
- 過去のコードへのリンクには、確認したコミットSHAを含むGitHubのURLを使う。

最後に、人が自分の目で読むべき場所を重要度順に3つまで挙げ、各箇所で何を判断するかを添える。
