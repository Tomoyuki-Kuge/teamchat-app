# プルリクエストの作成・更新

このSkillはPRを出す手順を扱う。命名、Issueとブランチの関係、本文の型、必要な証拠は、リポジトリの[AGENTS.md「ブランチとプルリクエストの方針」](../../../AGENTS.md#ブランチとプルリクエストの方針)を正本として参照する。規約やテンプレートをここに複写しない。

PR作成の依頼には、対象変更のコミット・pushとPR公開を含む。本文案だけを頼まれた場合は、コミット・push・公開を行わない。マージ、ブランチ削除、Docker・Gitの設定や接続トラブルの修復はこのSkillに含めない。

## 1. 対象と現在の状態を確かめる

- AGENTS.mdと関連するローカル指示を読み、ユーザーが指定したIssue、変更の目的、対象ブランチ、比較先を確認する。Issueに紐づかない変更も扱う。
- 作業ツリーの変更、ステージ済み変更、未追跡ファイル、比較先からのコミット差分を確認する。既にコミットされた変更も含め、PRに載る最終差分全体を読む。
- 対象ブランチの既存PRを確認する。対応する開いたPRがあれば更新し、重複して作らない。マージ済み・クローズ済みPRは再利用せず、今回の変更との関係を確かめる。
- 別目的の変更やユーザーの作業を、今回の変更として扱わない。対象の境界が判断できない場合だけ、該当ファイルと理由を示して確認する。
- main上で作業している場合は、AGENTS.mdの命名規約に沿う作業ブランチへ分ける。既存の作業ブランチを勝手に改名・上書きしない。

## 2. 受け入れ条件と検証根拠を整理する

- Issueの受け入れ条件、関連設計、会話で確定した追加決定を照合する。既存の要件は参照で示し、追加決定や設計変更は変更箇所と理由を説明できるようにする。
- 対象変更に必要な検証はAGENTS.mdに従う。現在の変更に対応する実行済み結果があれば再利用し、変更・失敗・未解決事項により必要になった確認を実施する。
- 自動テスト、静的確認、画面操作を区別する。条件ごとに、判定・確認方法・観測結果を対応付け、未実行や操作上の制約を隠さない。
- 画面変更ではスクリーンショットを用意し、何を確認した画像かを示す。文言やレイアウト変更前の画像しかない場合は、その限界を明記する。
- 判定できない条件は、足りない材料とともに未確認として記載する。PRを出すためだけに受け入れ条件や設計を弱めない。
- チェックの失敗を無視しない。原因と必要な対応を確認し、修正が依頼範囲を広げる場合は相談する。未達・未確認を含む状態での提出可否に判断が必要なら、公開前に具体的な状態を示す。

## 3. タイトルと本文を組み立てる

- AGENTS.mdの本文の型を読み、各欄を今回の変更に合わせて埋める。Issueなしの場合の関連欄・確認項目・末尾の扱いも、同じ規約に従う。
- タイトルと冒頭は、解決する課題と最終的な変更内容から書く。読み手が会話を知らなくても、なぜ必要で何が変わるか分かる説明にする。
- 計画の持ち方、技術選定、設計変更、対象外について説明を求められた場合は、材料・結論・理由を変更内容の中で整理する。設計の詳細はファイル・見出し・IDへの参照で示す。
- 途中で取り消した実装や会話の時系列を、最終変更と混ぜない。ただし、採用した判断の理由や制約を理解するために必要な経緯は残す。
- リポジトリ内の資料には相対パスやGitHubリンクを使い、ローカルの絶対パスをPRへ載せない。コードや証拠を特定する必要があれば、コミットSHAを含むリンクにする。
- 既存PRの更新では、現在の本文を読んでから書き換える。今も有効な判断・注意点・証拠画像を、理由なく削除しない。
- 複数行の本文は実際の改行を保持する。GitHub CLIを使う場合は一時ファイルに書いて --body-file で渡す。本文をシェルコマンドへ直接埋め込まない。

## 4. 対象だけをコミット・pushし、PRを作る

- コミット対象のファイルを明示してステージする。git add -Aやgit add .で、無関係な変更・個人設定・一時生成物をまとめて取り込まない。既にステージされた変更も、対象かどうか確認する。
- コミット前にステージ済み差分を確認し、意図した変更と検証結果が対応していることを確かめる。コミット件名はAGENTS.mdに従う。
- ローカルのGit操作にはGitを使う。GitHub上の参照・PR操作は、必要な機能を持つ接続済みGitHubツールを優先し、不足する操作は利用可能なGitHub CLIなどで行う。認証情報の表示や設定変更を、作成手順に混ぜない。
- pushは通常の更新で行い、認証エラーを理由にforce pushや無関係なブランチの取り込みを行わない。PRの作成先へ、意図したコミットが反映されたことを確認する。
- 新規PRでは、指定されたbase・headと、用意したタイトル・本文を使う。Draftの指定があれば従う。既存PRの更新では、ユーザーに指定されない限りDraft／レビュー待ちの状態を変えない。
- 作成やpushが失敗した場合は、原因に対応できる別手段があれば使う。状態を再確認してから再試行し、同じ失敗を繰り返さない。接続・権限の問題をこのSkill内で直せない場合は、本文案など完了できるものを残し、未完了の操作と理由を報告する。

## 5. 公開結果を確認して報告する

- 作成・更新後のPRを読み直し、URL、base、headのコミット、タイトル・本文、画像の参照先が意図どおりかを確認する。作成コマンドが成功しただけで完了としない。
- GitHub側の反映を確認できない場合は「確認済み」と書かない。pushだけ完了してPR作成が失敗した場合も、完了範囲を分けて伝える。
- 最後にPRのURLと、必要な未達・未確認・除外した変更を短く伝える。マージやブランチ削除へ自動で進まない。
