# テストのルール

## テストの追加・更新

- 機能の振る舞いを変更した場合は、関連するテストを追加または更新してください。
- 受け入れ条件をテストケースに反映し、条件ごとに結果を確認できるようにしてください。
- 依頼に含まれる既存動作の維持も、必要に応じて回帰テストで確認してください。
- テストは独立して実行できるようにし、既存データや他のテストの実行順に依存させないでください。

## チームチャット機能で確認する条件

変更した機能に応じて、`docs/design/acceptance.md`の該当条件を確認してください。特に、次の観点を含めてください。

- ログインが必要な操作で未認証アクセスを拒否する。
- プライベートチャンネルの未参加者に、チャンネル情報やメッセージを一覧・検索・APIから漏らさない。
- チャンネル作成者とメッセージ投稿者の権限を守り、投稿者はログイン中の利用者から決定する。
- 必須項目、文字数上限、関連データの制約に違反した入力を保存しない。エラー表示は設計・モックの文言に沿う。
- メッセージ・返信の表示順、編集済み表示、削除状態、返信件数、ページ送りなど、変更対象に関係する既存動作を保つ。
- 公開APIにプライベートチャンネルや認証が必要なデータを含めない。

## 応答だけでは確認できない条件

変更対象に関係する場合は、次の検証を追加してください。期待する判定順序・保存状態・表示範囲は、`docs/design/`の関連する契約に従います。

- **判定順序**：不正入力と、対象不存在・親子関係の不整合・権限不足・削除状態などを組み合わせ、設計で優先する応答になることを確認する。各条件を単独で試すだけで済ませず、対象と権限が正しい場合の入力エラー応答も確認する。
- **拒否後の保存値不変**：拒否される更新・削除の直前と直後にDBから値を再取得し、変更されてはいけない保存項目を厳密比較する。応答ステータスや行数だけで判断せず、本文・版・日時・関連IDなども確認する。他人の操作には有効な変更用入力も使い、入力不正とは独立して認可による拒否を確認する。成功操作や前提データの変更を挟む場合は、比較元を拒否操作の直前に取り直す。
- **表示範囲**：ページや取得件数の境界を超えるデータを用意し、表示対象・除外対象・並び順をID配列などで比較する。件数やURLの保持だけで判断せず、履歴追加・成功・入力エラー・新着追加のうち変更対象に関係する操作で実際の表示範囲を確認する。独立した一覧がある場合は一覧ごとに検証し、別の一覧・親・チャンネルのデータが混ざらないことも確認する。日時や新着保存時刻は必要に応じて固定し、実行時刻やランダムな順序に依存させない。

- **同時操作**：同時操作の整合性を変更した場合は、必要に応じて独立したDB接続で実際のロック待ちと確定後の保存状態を検証する。固定時間のsleepだけで操作順を仮定せず、同期イベントやDBの待機情報で状態を確認する。別接続から見える準備データを用意し、testing DBだけを使う。タイムアウトと、失敗時もプロセス・接続・ロック・準備データを片付ける処理を設ける。Actionの差し替えによる状態変更と実際の並行実行は、検証結果を分けて報告する。

## 実行

- Docker Desktop を起動し、テストは `./vendor/bin/sail artisan test` で実行してください。
- `./vendor/bin/sail artisan test --filter=ChannelTest` # チャンネル関連のテストを絞る例
- 失敗した場合は原因を修正して再実行してください。実行できない場合は、理由と未確認範囲を作業報告に記載してください。
- テストが落ちた状態で作業を終えない。原因が自分の変更以外にあっても直す。
