### △の条件と共通の前提

- **F-04・F-06・F-11・F-12・F-15・F-16**：対象が公開、または本人が追加されたプライベートであること。一覧自体はログイン社員なら開けるが、表示・切り替え先をこの範囲に絞る。作成者は自動で所属し、外せない（仕様 §3-2・§3-3、Q-03、A-04）。
- **F-09・F-10**：対象がプライベートであること。追加・解除は作成者だけが行い、作成者本人の解除を拒否する。公開チャンネルには管理操作を設けない（仕様 §3-3、members.html）。
- **F-13・F-14**：現在も閲覧・投稿できるチャンネル内の、本人が書いた未削除の通常投稿・返信であること。作成者にも他人の本文を変更・個別削除する権限はない。メンバー解除後は自分の過去投稿であっても操作できない（仕様 §3-2〜§3-4）。
- **F-17**：通常投稿・返信の本文を検索し、公開と参加中プライベートに限定する。削除済みチャンネル・削除済みメッセージを件数計算とページ分割の前に除外する。他チャンネルの作成者というだけでは検索範囲を広げない（Q-09・Q-10・Q-14・Q-24・Q-26）。
- **F-19**：指定先が未削除の公開チャンネルであること。ログインや所属の有無にかかわらず、プライベートの情報は返さない（仕様 §3-7）。
- **F-20**：その人が利用できる入力操作だけに適用する。未ログインでは登録・ログイン、ログイン後は権限のあるフォームが対象（仕様 §5-1、screens.md）。
- **F-21**：未ログインでは認証画面の共通表現を利用する。チャンネル・検索・メンバーなどログイン後の共通画面は利用できない（login.html、register.html）。
- 全区分で、チャンネル削除時は配下の全投稿・全返信を未編集・編集済み・個別削除済みの区別なく終了させ、本文・削除表示・返信件数を含め利用対象外とする。チャンネルが存続する間だけ、個別削除済みの行は会話・スレッドで削除表示とし、個別削除済みの通常投稿への返信の閲覧・追加を認める（Q-06・Q-17・Q-24〜Q-26）。F-06の未ログイン欄は通常画面の閲覧・投稿を指し、登録・ログインとF-18・F-19は別に扱う。
- F-22・F-23は初期データ投入であり、利用者が実行する画面・APIを作らない。専用の管理者区分を追加しない（仕様 §4・§5-4）。

画面でボタンを隠すことに加え、各リクエストでサーバー側も認可する。対象を閲覧できるかを先に判定し、未参加プライベートには不存在と同じ404を返す。その後、作成者・投稿者本人かを判定する（Q-03、仕様 §3-7）。

## ルーティング一覧（通常画面）

`{channel}`・`{message}`・`{user}`は整数ID。メッセージはURLのチャンネルに属することを確認し、スレッドの`{message}`には同じチャンネルの通常投稿だけを許可する。返信先の親は個別削除済みでもよい。保護された画面は未認証・ログインの有効期限切れなら302で`/login`へ移動する。登録・ログイン画面は未ログイン向けとし、ログイン済みなら302で`/channels`へ移動する。

|:--|:--|:--|:--|:--|
| GET | `/login` | ログインフォーム | 200 SC-01 | 未ログイン、F-02 |
| POST | `/login` | `email`, `password` | 303 `/channels` | 未ログイン、F-02・Q-08 |
| GET | `/register` | 登録フォーム | 200 SC-02 | 未ログイン、F-01 |
| POST | `/register` | `name`, `email`, `password`, `password_confirmation` | 自動ログインし303 `/channels` | 未ログイン、F-01・Q-08 |
| POST | `/logout` | ログアウト | セッションを無効化し303 `/login` | ログイン、F-03 |
| GET | `/channels` | 閲覧できるチャンネル一覧・作成順 | 200 SC-03 | ログイン、F-04・F-06 |
| GET | `/channels/create` | 作成フォーム | 200 SC-04 | ログイン、F-05 |

| GET | `/search` | `q`（必須）, `sort=newest`（既定）または`oldest`, `page`（既定1）, `until_id`（初回のID上限） | 200 SC-07、10件ずつ | ログイン、F-17・Q-31 |

- PATCH・DELETEはHTMLフォームのPOSTに`_method`を付けて送る。POSTを含むすべての変更操作で、認証判定の前にCSRFトークンを検証する。不正・有効期限切れなら419で送信を拒否し、登録・変更・削除を行わない。画面を開き直して送信し直すよう案内する。GET・HEADでデータを変更しない。`/channels/create`はIDを取るルートより先に照合する。
- 登録・ログイン成功時は認証セッションIDを更新し、ログアウトではセッション無効化とCSRFトークンの更新を行う。パスワードは登録時8〜128文字、変換・切り捨てなし、ハッシュ方式はArgon2idとする。ログインには登録用の最小8文字チェックを流用しない（Q-38）。認証状態の具体的な保存先はdata.md末尾の実装設計事項として残す。
- メールは登録・ログインの両方で前後空白・改行を除去し、ドメインの英字を小文字に揃えてから形式・255文字以内を確認し、照合する。切り捨てず、`@`より前の大小・全角半角・Unicodeの表記差は変換しない。チャンネル名はこれらの差をすべて区別し、保存値や削除確認名を自動でtrim・正規化しない。未削除の名前の厳密な一意性はバリデーションとDB制約を併用する（Q-32・Q-33・Q-37）。検索専用の正規化は保存・認証の照合には流用しない。
- 作成時の作成者・投稿時の投稿者はログイン社員からサーバーで設定する。入力された作成者ID・投稿者ID・`deleted_at`などを保存対象にしない。メンバー追加で既に所属していれば変更なし、解除で既に所属していなければ変更なしで同じ成功先へ戻す。作成者解除は403、登録されていない社員IDは入力エラーとする（今回はこの再送時の扱いを技術設計として定める）。
- 本文の編集開始はSC-05／SC-06のURLへ`edit={message ID}`を付けて再表示し、本文と同時に取得した`version`を`expected_version`のhidden入力へ入れる。正の整数を必須とし、サーバーの保存値へ直接代入しない。「やめる」は`edit`を外したURLへ戻る。編集対象が当該一覧・スレッドの範囲にあること、本人で未削除であることも検証する。削除済みの本文を編集欄・SC-10へ再出力しない。
- 編集確定時に版が異なれば保存せず409で元のSC-05／SC-06の編集位置を再表示し、現在保存されている本文と自分の入力を確認できるようにする。確認後のフォームには、その本文と同時点の現在版を入れ、再送でも版を照合する。最後に成功した保存を採用する（Q-30、behavior.md）。
- SC-08の削除確認はGETの`confirm_delete=1`で開き、「やめる」は同パラメータを外す。`confirmation_name`の一致だけで認可を代用せず、削除確定時も作成者・未削除を確認する。件数は通常投稿・返信それぞれを削除済みも含めて集計する（data.md）。
- 作成・改名で未削除の他チャンネルと名前が重複した場合は、公開／プライベートにかかわらず「使用できない名前です」と表示する。重複が理由であることや既存チャンネルの情報・公開種別を説明しない。同時操作による一意制約違反も同じ文言へ変換する（Q-28）。
- SC-09は、入力語全体が表示名またはメールに部分一致する登録済み社員を候補とし、表示名昇順・同名ならID昇順にする。既存メンバーを除外し、空白だけを含む空検索は未実行として候補を出さない。検索0件は正常な0件案内とする。本文検索の複数語ANDを流用しない（Q-29）。
- 画面の入力制約と文言はscreens.mdを使う。変更フォームの入力エラーは303で同じフォームへ戻し、エラーと非機密の入力を保持する。GETの不正な検索・表示パラメータは更新せず422の同画面で案内する。チャンネルや親子関係を見せられない場合は入力エラーより先に404にする。
- 通常投稿・返信のフォームは、入力エラー時に戻す通常投稿・返信の表示範囲をhiddenで保持する。SC-06の通常投稿には`origin=thread`と開いている親IDの`thread`を渡す（SC-05は省略時`origin=channel`）。返信の親はパスから取得する。303の戻り先は検証済みの親ID・表示範囲から生成し、SC-06ではスレッドを開いたまま、送信した欄だけに本文のOld Inputとエラーを表示する。通常投稿・返信・編集の入力とエラーは操作種別と対象IDに対応付け、別の欄へ流用しない。成功時の遷移はルート表どおりとする（Q-34）。
- 本文編集の入力エラーでは、入力本文と送信時の`expected_version`をセットで保持する。GETの再表示で版だけを最新へ置き換えて、未確認の変更を上書きできる状態にしない。
- チャンネル削除の入力エラーは`/channels/{channel}/edit?confirm_delete=1`へ戻し、確認欄を開いたままエラーを表示する。メンバー追加では検索語`q`をhidden入力で引き継ぎ、成功・入力エラー後のSC-09でも保持する。
- F-20・F-21は全画面に適用する横断要件、F-22・F-23は初期投入であるため、個別ルートを増やさない。

### リンクで引き継ぐ表示範囲と戻り先

Q-11・Q-15・Q-18の動作を満たすため、次のパラメータを今回の設計として定める。通常投稿・返信の並びは`(created_at, id)`で一意にし、取得した範囲を古い順に表示する。同じ日時はIDが小さい方を古いものとする。

| パラメータ | 意味・検証 |
|:--|:--|
| `messages_until`, `messages_pages` | 初回取得時の最新の通常投稿ID（取得範囲の上限）と、表示する10件単位の数（既定1）。上限IDの`(created_at, id)`以下から最新`10 × messages_pages`件を取り、古い順に表示する。「以前のメッセージを表示」は上限IDを保って単位数を1増やす。空一覧では上限を付けない |
| `replies_until`, `replies_pages` | SC-06の返信に同じ方式を独立適用する。返信IDはそのスレッドに属することを確認する。親は常に表示し、全返信件数はこの取得件数とは分ける |
| `focus` | 検索結果などの対象メッセージID。通常投稿ならSC-05、返信なら親のSC-06へリンクする。初回は対象を含む10件（対象を上限とする範囲）を生成し、`#message-{ID}`へ移動する。以後のリンクは生成した表示範囲を引き継ぐ |
| `edit` | インライン編集対象のメッセージID。SC-05では通常投稿、SC-06では表示している通常投稿または当該スレッドの返信に限る |
| `origin`, `thread` | 編集確定・SC-10・削除確定の操作元と、通常投稿の入力エラー時の復帰先。`origin=channel`または`thread`。後者の`thread`は元のSC-06の親IDで、同じチャンネルの通常投稿に限る。編集・削除の省略時は対象自身（通常投稿）またはその親IDから導出し、新規通常投稿の省略時はchannelとする |

上限・対象IDのチャンネル／親子関係、単位数が1以上の整数であることを検証する。削除済みの行も位置を保つので表示境界に使える。過去分追加リンクは、追加前の最古の行の`#message-{ID}`を付けて読んでいた位置へ戻す。表示済みの行を残し、新着は自動追加しない。最新範囲へ戻るには表示範囲を外して開き直す。

編集・削除確認には`origin`・`thread`・必要な表示範囲を渡し、フォームのhidden項目と中止リンクにも保持する。戻り先は検証済みのID・範囲からサーバーが生成したSC-05／SC-06のURLだけとし、任意の`return_url`やRefererに任せない。削除確定後も中止後も元の画面へ戻る（Q-23）。返信投稿後は通常投稿の表示範囲を保ち、返信だけ最新10件に戻す。

投稿の入力エラーでは、`messages_until`, `messages_pages`, `replies_until`, `replies_pages`のうち元画面で使っていた値を保持する。正常投稿時の最新範囲への移動と区別し、通常投稿からのエラーでも元がSC-06なら該当スレッドを維持する。復帰先のチャンネル・親・所属は現在値で再確認する（Q-34）。

### 検索用の比較と強調表示（Q-35）

本文検索・メンバー候補検索とも、検索語と対象テキストの比較用の値だけをUnicode NFKC正規化し、英字を小文字にする。保存する原文は変えず、登録・一意性・ログインの比較規則（Q-32）とは分ける。`abc`・`ABC`・`ＡＢＣ`、半角カナと対応する全角カナ、`①`と`1`などを同一視する。

本文は正規化後の検索語を空白で分割して複数語ANDで部分一致検索し、メンバー候補は正規化後の入力語全体を表示名またはメールへ部分一致検索する。メンバーの表示名→ID順と既存メンバー除外は維持する。正規化後の`%`・`_`は通常の文字として扱い、SQLの部分一致に渡す際にエスケープする。一致語の強調は正規化済み文字列の位置をそのまま使わず、対応する元本文の範囲に付ける。

検索は`(created_at, id)`を両方降順／両方昇順にする。初回は閲覧・未削除・本文検索の条件に一致するメッセージの最大IDを`until_id`とし、現在の条件と`id <= until_id`を適用してから件数を数え、10件ずつ分割する。ページ移動リンクでは検索語・並び・上限IDを保持する。検索語・並びを変えるか先頭から検索し直すときは`page=1`に戻し、上限も取り直す（Q-31）。部分一致の入力に含まれる`%`・`_`はワイルドカードではなく文字として扱う（Q-10を満たす技術設計）。

検索・公開APIの`until_id`は0以上の整数とし、0は初回0件を表す。検索の`page`もAPIと同様に1以上の整数とし、不正な値は422にする。表示の上限であり、対象行の存在確認・閲覧権限の代わりにはしない。上限を引き継げば、その値より大きいIDの追加は途中のページへ混ざらない。削除、本文編集による検索対象の変化、所属変更によるずれは残り、初回の本文・全ID一覧を保存する時点固定ではない。検索と同じ方式を、以下の公開APIにも適用する。

検索画面では、現在の条件とID上限を適用した総件数から`last_page = max(1, ceil(total / 10))`を求め、有効な`page`がこれを超えた場合は、検索語・並び順・同じ`until_id`を維持して最後のページへ302リダイレクトする。全体0件なら1ページ目で通常の0件案内を表示する。不正なpageの422とは区別し、公開APIの範囲外ページ200・空配列には適用しない（Q-36）。

## 公開APIの共通契約

根拠は仕様 §3-7、Q-06・Q-12・Q-13・Q-15・Q-24・Q-26。次の2種類だけを提供し、画面用の変更ルートを公開APIにはしない。

| 項目 | 契約 |
|:--|:--|
| 形式・認証 | JSON、`Content-Type: application/json; charset=utf-8`。認証・APIキー不要で、ログイン状態によって返却範囲を変えない。リクエスト本文は不要 |
| メソッド | GET。HEADは同じステータス・ヘッダーで本文なし。既知のAPI URLへの他メソッドは405、`Allow: GET, HEAD`。API配下の存在しないURLは404 |
| 共通クエリ | `page`と`until_id`。page省略は1、1以上の10進整数。until_id省略時はそのリクエストで初回上限を算出し、指定時は0以上の整数。小数・空文字・配列・数値以外、pageの0・負数、until_idの負数は422。ページサイズは固定。未提供の検索・並べ替え・利用者フィルター等は適用しない |
| ID | パスの`channel`は正の整数ID。形式不正も、対象なしと同じ404。名前をIDの代わりに受け付けない |
| 時刻・型 | ID・件数・ページはJSON整数、編集有無は真偽値。`created_at`は秒までのISO 8601、JSTオフセット付き（例：`2026-08-17T09:12:00+09:00`）。画面の`YYYY/MM/DD HH:mm`とは表現を分ける |
| 返却項目 | 以下の明示した項目だけを組み立て、DB行をそのままJSON化しない。メールアドレス・パスワード・削除済み元本文・プライベートの名前などを含めない |
| ページリンク | 同じAPIへの相対URLにpageと同じuntil_idを付ける。`links.prev`は`page > 1`なら前ページ、1ならnull。`links.next`は続きがある場合だけ次ページ、それ以外はnull。`meta.last_page`は0件でも1とする。最新を取得し直すときはuntil_idを外してpage=1から開始する |
| 空・範囲外 | 一覧0件、または最終ページより大きい有効な`page`は200。チャンネルAPIは`data: []`、メッセージAPIは`data.messages: []`と`data.replies: []`を返す。不存在・非公開チャンネルを空一覧200で表さない |

ページ番号と初回の最大IDを使う方式を[Q-31](questions.md#今回追加した確認事項)で採用した。上限は各APIの現在の返却対象から算出する。プライベートを含む全チャンネルの最大IDを返さない。上限が改変されても現在の公開・未削除条件を必ず適用し、指定IDの存在や種別を返さない。件数・最終ページ・リンクは各リクエストの「現在の公開・未削除条件＋ID上限」で算出する。新規IDの混入を抑えるが、削除等による重複・読み飛ばしは残る。公開範囲・削除状態・ID上限の条件は、必ず件数計算・ページ分割より前に適用する。

### GET `/api/channels`：公開チャンネル一覧（F-18）

入力は共通の`page`・`until_id`。初回上限は`channels.deleted_at IS NULL AND is_private = false`を満たす最大ID（0件なら0）。この条件と`id <= until_id`を対象に、`(created_at, id)`昇順で1ページ10件取得する。各要素は`id: integer`、`name: string`、`description: string|null`のみ。`meta.until_id`は引き継ぐ上限の整数、`meta.total`は現在その条件に一致する全チャンネル数、`per_page`は10、`last_page = max(1, ceil(total / 10))`とする。

リクエスト例：`GET /api/channels?page=1`。以下は公開チャンネルが3件ある場合の200応答例であり、ID・件数を固定データの要件にはしない。

```json
{
  "data": [
    { "id": 1, "name": "全体連絡", "description": "全員に共有したいこと" },
    { "id": 2, "name": "開発", "description": "開発に関する相談と報告" },
    { "id": 3, "name": "雑談", "description": null }
  ],
  "meta": { "current_page": 1, "until_id": 3, "per_page": 10, "total": 3, "last_page": 1 },
  "links": { "prev": null, "next": null }
}
```

例えば公開チャンネルがID1〜11の11件なら、初回の`meta.until_id`は11、`links.next`は`/api/channels?page=2&until_id=11`となる。初回1ページ目で0件なら`data: []`、`until_id: 0`、`total: 0`、`last_page: 1`、両リンクnull。

### GET `/api/channels/{channel}/messages`：公開メッセージ一覧（F-19）

入力はパスの`channel`と共通の`page`・`until_id`。先にチャンネルが未削除かつ公開であることを確認する。プライベート・削除済み・不存在はすべて同じ404とし、クエリの検証よりも先にこの判定を行う。

初回上限は、そのチャンネルの`messages.deleted_at IS NULL`の通常投稿・返信を合わせた最大ID（0件なら0）。共通の`id <= until_id`を適用し、`parent_message_id IS NULL`の通常投稿と、NULLでない返信を別枠にして、どちらも`(created_at, id)`降順とする。ページpでは、それぞれ先頭から`5 × (p - 1)`件を飛ばして最大5件ずつ取得する。合計が10件未満でも他方で補充せず、返信を個人で絞らない。親が別ページ・個別削除済みでも未削除返信は返す（Q-13・Q-15・Q-31）。

| 返却項目 | 型・意味 |
|:--|:--|
| `data.messages`, `data.replies` | 通常投稿・返信それぞれの配列。混ぜて並べ替えない |
| 各要素の`id`, `parent_message_id` | integerとinteger／null。通常投稿は親null、返信は必ず親IDを持つ |
| 各要素の`body`, `author_name`, `created_at`, `is_edited` | 本文string・投稿者表示名string・投稿日時string・`edited_at`の有無によるboolean。メールや投稿者のアカウント情報を付加しない |
| 各要素の`reply_count` | integer。通常投稿に付いた全返信数で、削除済み返信も含む。返信は階層1段なので0。配列に含まれた返信数とは別の値 |
| `meta.current_page`, `meta.per_type` | 要求したページ番号、各枠の上限5 |
| `meta.until_id` | 通常投稿・返信へ共通適用する初回のID上限。次のリンクでも同じ値を引き継ぐ |
| `meta.messages_total`, `meta.replies_total` | それぞれID上限内の未削除の通常投稿数・返信数。削除済みの親に付いた未削除返信も後者へ含める |
| `meta.last_page` | `max(1, ceil(messages_total / 5), ceil(replies_total / 5))`。合計件数を10で割って求めない |
| `links.prev`, `links.next` | このチャンネルのAPIへのpage・until_id付きリンク。いずれか一方の枠に続きがあればnextを返す |

リクエスト例：`GET /api/channels/2/messages?page=1`。未削除の通常投稿1件・返信2件がある200応答例。親101には削除済み返信2件もあるため`reply_count`は3となる。親90は個別削除済みで、本文も親レコードも返さないが、未削除返信202の親IDは維持する。

```json
{
  "data": {
    "messages": [
      {
        "id": 101,
        "parent_message_id": null,
        "body": "おはようございます。9月リリースの日程を今週中に確定させたいです。",
        "author_name": "鈴木 花子",
        "created_at": "2026-08-17T09:12:00+09:00",
        "is_edited": false,
        "reply_count": 3
      }
    ],
    "replies": [
      {
        "id": 202,
        "parent_message_id": 90,
        "body": "更新を確認しました。ログインできています。ありがとうございます。",
        "author_name": "高橋 健",
        "created_at": "2026-08-17T11:02:00+09:00",
        "is_edited": true,
        "reply_count": 0
      },
      {
        "id": 201,
        "parent_message_id": 101,
        "body": "承知しました。検索まわりの実装は木曜に終わる見込みです。",
        "author_name": "高橋 健",
        "created_at": "2026-08-17T09:20:00+09:00",
        "is_edited": false,
        "reply_count": 0
      }
    ]
  },
  "meta": {
    "current_page": 1,
    "until_id": 202,
    "per_type": 5,
    "messages_total": 1,
    "replies_total": 2,
    "last_page": 1
  },
  "links": { "prev": null, "next": null }
}
```

例えば初回上限212で通常投稿2件・返信12件なら、1ページ目は2＋5件、2ページ目は0＋5件、3ページ目は0＋2件となる。2ページ目は合計5件でも`next: "/api/channels/2/messages?page=3&until_id=212"`を返す。削除済み返信は配列・`replies_total`から除外するが、各親の`reply_count`からは引かない。reply_countは現在の全返信件数なので、初回上限より後に付いた返信も含む（Q-06・Q-15）。

初回1ページ目で通常投稿・返信とも0件なら両配列は空、`until_id: 0`、`messages_total: 0`、`replies_total: 0`、`last_page: 1`、両リンクnullとする。

### APIのエラー応答

エラーは成功時の`data`・`meta`・`links`を付けず、次の`error`オブジェクトへ統一する。`code`は機械判定用の固定値、`message`は案内文、`details`は入力項目名→文言配列のオブジェクト。項目に結び付かないエラーでは`details: {}`。認証画面へのリダイレクトやHTMLの例外ページを返さない。

| HTTP | code | message・用途 |
|:--|:--|:--|
| 404 | `NOT_FOUND` | `対象が見つかりません`。不正ID・不存在・プライベート・削除済みを区別しない |
| 405 | `METHOD_NOT_ALLOWED` | `このHTTPメソッドは使用できません`。書き込みは実行せず、Allowヘッダーを付ける |
| 422 | `VALIDATION_ERROR` | `入力内容を確認してください`。不正なpage・until_id。対象チャンネルが非公開等なら、こちらより404を優先 |
| 500 | `INTERNAL_ERROR` | `処理に失敗したため時間をおいて再度お試しください`。SQL・スタックトレース・元本文を返さない |

`GET /api/channels/4/messages?page=1`で対象がプライベートの場合も、対象が存在しない場合も同じ404応答にする。

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "対象が見つかりません",
    "details": {}
  }
}
```

`GET /api/channels?page=0`の422応答例：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください",
    "details": { "page": ["pageは1以上の整数で指定してください"] }
  }
}
```

不正なuntil_idは同じ422形式で`details: { "until_id": ["until_idは0以上の整数で指定してください"] }`を返す。405・500も同じ構造で、表のcode・messageと空のdetailsを返す。API利用にログインを要求しないため401は返さず、プライベートの存在を示す403も返さない。公開APIの返信件数に削除済みを含めることはQ-06・Q-12の決定であり、削除済みの本文・レコードを返すこととは分ける。

## 設計間の照合と確認が必要な点

- 権限はF-01〜F-23、通常画面はSC-01〜SC-10、公開APIはF-18・F-19の2種類を対応させた。通常投稿・返信の取得条件、削除保持、件数、SC-10の独立URL・戻り先はscreens.md・data.md・behavior.mdと揃える。
- **名前一意と存在非開示の扱い（決定済み）**：[Q-28](questions.md#今回追加した確認事項)のユーザー指定に従い、同名禁止を維持し、エラーを「使用できない名前です」に統一して重複という理由やプライベートの存在を説明しない。作成可否からの推測を完全に防ぐ保証とは区別する。この方針は未決事項から外す。
- メンバー候補の条件（Q-29）、保存前の競合確認（Q-30）、初回ID上限（Q-31）、チャンネル名とメールで分ける同一判定（Q-32）は[確認事項](questions.md#今回追加した確認事項)のユーザー決定を反映した。Q-31の削除等によるページずれ、Q-32の見分けにくいチャンネル名は採用方針の注意点として残す。
